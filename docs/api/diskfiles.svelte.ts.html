track_changes

Starts recording what handle_change is given. Start it before requesting a file-tree snapshot and pass it to add_initial or reconcile with the snapshot, which is then applied around what filer_change reported while the request was in flight:

  • A path an add, change, or delete reported keeps what the notification left: the snapshot's entry for it is skipped, and it isn't pruned. So a file deleted meanwhile isn't resurrected and newer content isn't reverted.
  • A touch never makes the snapshot yield, because it carries no contents: a client that missed a change while disconnected holds old text, and only the snapshot can replace it. The snapshot's entry is applied (or the file pruned, if the snapshot lacks it), and then the path's latest touch is applied again — unless an add, change, or delete was also reported for the path, whose result already stands.

The touch's metadata wins over the snapshot's whichever mtime is higher. The two can't be ordered from here — a notification that arrives during the request may have been sent before or after the backend read its index for the snapshot, and a file's mtime can move backwards — but the backend queues a notification for every change to its index, so its notifications converge on the index: if the snapshot was the newer of the two, whatever moved the file past the touch has its own notification still to come, and that one settles it. Preferring the snapshot would have no such correction when the touch was the newer.

touch

Applies a touch: the file's metadata changed on disk and the contents the backend holds for it did not, so the diskfile keeps the content it has — loaded or not — and takes the new mtime. For a file whose content isn't loaded the backend holds none, so every change to it arrives this way. Nothing else changes: no editor state is notified, since there's no new content to weigh against a draft.

A path this client doesn't hold is left alone (there are no contents to add it with — the next snapshot brings it), as is a diskfile kept after its file was deleted, whose content is no longer the file's.

upsert

Adds a diskfile for disknode, or updates the existing one at the same path in place — keeping its id, so tabs, selection, and parts stay attached. A diskfile kept after a delete (see remove_by_path) is reattached this way when its path reappears on disk. An existing diskfile whose content and dependency data already match is left untouched but for its mtime, so a resync that re-sends every file doesn't churn the unchanged ones. A content change is recorded in the file's editing state, if it has one (DiskfileEditorState.check_disk_changes).

reconcile

Replaces the file tree under roots with a session snapshot's: upserts every snapshot file (like add_initial), and removes each known file under a root that the snapshot lacks, via remove_by_path — so a file open with unsaved edits is kept, flagged deleted_on_disk. Files outside every root are left alone, since the snapshot says nothing about them.
